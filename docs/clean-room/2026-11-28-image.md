# Image (contrast, saturation, sharpness, hue)

## Source and method

2026-11-28. One USB capture with USBPcap (snap length 512, device address 1
on the camera's root hub `\.\USBPcap2`, descriptors injected), Gimbly
closed, OBSBOT Center the only app using the camera. Claude Code went
through every control of the **Image** section at the bottom of the
**Image** tab of the visible OBSBOT Center UI, one action at a time with a
few seconds between them, and checked the UI after each one. The capture
stays outside the repository and was decoded with our own script.

## Setup

- Camera: OBSBOT Tiny 3 Lite, USB `3564:ff04`, firmware `6.5.11.1` (not
  reread).
- Official app: OBSBOT Center `v2.0.17.532` (not reread).
- OS: Windows 10 Pro 19045.
- No AI mode running, preview closed, Auto Exposure and Auto WB on.

## Observed: the UI

- The header shows **Image**, a round-arrow reset icon after the title and a
  caret on the right that folds the section. Folded, only the header stays.
- Four rows, each a label, a slider and a number field with arrows:
  **Contrast**, **Saturation**, **Sharpness**, **Hue**. All four are 50 by
  default.
- Every slider runs from 0 at the left end to 100 at the right. Arrows step
  1 and stop at the ends.
- Typed `37` was taken. In `150` the field refused the last digit, which
  would pass 100, and kept `15`.
- A click on the track beside the handle moved the value 10 towards the
  click (100 → 90 → 80), not to the click.
- The mouse wheel over a slider scrolled the panel, not the value.
- No tooltips on the labels or the reset icon, no right-click menus.
- Reset icon: all four back to 50.
- The values survived camera sleep. After an OBSBOT Center restart with the
  camera asleep, all four fields showed 100; after waking, the next change
  showed the camera's real values (61, 7, 44).

## Observed: USB

No vendor messages. Every control is a standard UVC processing unit control
(unit 3, interface 0), `SET_CUR` and `GET_CUR` only, 2 bytes little endian:

| Row | Selector | UVC name |
| --- | --- | --- |
| Contrast | 3 | `PU_CONTRAST_CONTROL` |
| Hue | 6 | `PU_HUE_CONTROL` |
| Saturation | 7 | `PU_SATURATION_CONTROL` |
| Sharpness | 8 | `PU_SHARPNESS_CONTROL` |

- Values are the numbers shown: `0000` for 0, `3200` for 50, `6400` for 100.
- While dragging, the app sent a few writes per drag (start, middle, end).
  Typing sent one write per keystroke (`2` then `23`).
- Reset: four writes of 50 within a millisecond, Contrast, Saturation,
  Sharpness, Hue.
- On start and wake the app read all four (`GET_CUR`), twice each.
- On the restart at 12:41:53, with the camera asleep, every read answered
  `c063` (25536). That is why the fields showed 100.

## Inferred

- The fields clamp what they read to 0-100, so the sleeping camera's
  answer showed as 100.
- Standard UVC controls work the same through each OS camera API
  (`IAMVideoProcAmp` on Windows, V4L2 on Linux, UVC requests on macOS).

## Unknown

- The camera's own `GET_MIN`/`GET_MAX`/`GET_DEF` for these controls; the
  official app did not ask. Gimbly uses 0-100 with 50 as the default, as
  observed.
- Whether other models use the same ranges.

## Tests

- `camera::control::tests::image_values_out_of_range_are_refused` checks a
  read of 50, the ends, and that the sleeping camera's `0x63c0` is refused.
- `app::view_image::tests` check typed values (`150` refused) and the order
  of the four values.

## Checked in Gimbly

2026-11-28, same camera and OS, OBSBOT Center closed:

- `gimbly --probe --virtual-camera --gimbal DIR wake image:0,50,50,50 …
  image:50,50,50,100 image:23,61,7,44` sent every step without an error and
  saved a frame after each with the virtual camera running. The first
  status read 50 for all four. The snapshots were flat at Contrast 0 and
  harsh at 100, grey at Saturation 0 and vivid at 100, pinker at Hue 0 and
  yellower at 100.
- The next probe process read back 23, 61, 7, 44, then `image:50,50,50,50`.
- In the running app (Image tab): the section read 50 for all four; Contrast
  dragged to 0, Saturation typed `37`, Sharpness up arrow (51), Hue typed
  `150` (refused), Hue dragged to 95; the reset tooltip; reset (all 50);
  fold.
- Unlike the official app, a click on the track moves the handle to the
  click, as on the other Gimbly sliders, and a reading out of range is
  treated as not read yet (retried after wake) instead of shown as 100.
- The camera was left at 50 for all four.
